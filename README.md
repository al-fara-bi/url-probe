# url-probe

Сервис асинхронной проверки списка URL: REST API на NestJS и SPA на React.

Пользователь отправляет список ссылок, сервис создаёт задание и проверяет каждую ссылку
в фоне HEAD-запросом, не более 5 одновременных проверок на задание. Интерфейс опрашивает
статус задания и показывает прогресс, HTTP-коды и ошибки по каждой ссылке. Задание можно
отменить в любой момент — уже начатые запросы прерываются, ещё не начатые не запускаются.

## Стек

| Слой | Технологии |
|---|---|
| Бэкенд | Node.js 22, TypeScript, NestJS 11, Jest |
| Фронтенд | TypeScript, React 19, Zustand, Vite, Vitest |
| Инфраструктура | Docker, docker compose, nginx |

Хранение — in-memory, база данных не требуется.

## Запуск через Docker

```bash
docker compose up --build
```

- Интерфейс: http://localhost:8080
- API: http://localhost:3000

nginx отдаёт собранный фронтенд и проксирует `/api` на бэкенд, поэтому CORS не нужен.

## Локальный запуск

Требуется Node.js 22 или новее — используются `fetch`, `AbortSignal.any()` и
`AbortSignal.timeout()`.

Бэкенд:

```bash
cd backend
npm install
npm run start:dev     # http://localhost:3000
```

Фронтенд (во втором терминале):

```bash
cd frontend
npm install
npm run dev           # http://localhost:5173
```

Dev-сервер Vite проксирует `/api` на `http://localhost:3000`.

## Тесты

## API

### `POST /api/jobs`

Создаёт задание и сразу запускает обработку в фоне.

```json
{ "urls": ["https://example.com", "https://github.com"] }
```

Ответ `201`:

```json
{ "jobId": "493e33ce-f829-4391-b85e-6841ca9f9e0b" }
```

Ответ `400`, если список пуст, содержит больше 1000 элементов или невалидные ссылки:

```json
{
  "message": ["not valid http(s) URLs: not a url, also-bad"],
  "error": "Bad Request",
  "statusCode": 400
}
```

### `GET /api/jobs`

Список заданий, новые первыми.

```json
[
  {
    "id": "493e33ce-f829-4391-b85e-6841ca9f9e0b",
    "createdAt": "2026-07-26T13:29:15.436Z",
    "status": "in_progress",
    "total": 4,
    "processed": 2,
    "succeeded": 1,
    "failed": 1
  }
]
```

### `GET /api/jobs/:id`

То же самое плюс детали по каждой ссылке. `404`, если задание не найдено.

```json
{
  "id": "493e33ce-f829-4391-b85e-6841ca9f9e0b",
  "createdAt": "2026-07-26T13:29:15.436Z",
  "status": "completed",
  "total": 2,
  "processed": 2,
  "succeeded": 1,
  "failed": 1,
  "urls": [
    {
      "url": "https://example.com",
      "status": "success",
      "httpStatus": 200,
      "startedAt": "2026-07-26T13:29:15.437Z",
      "finishedAt": "2026-07-26T13:29:24.662Z",
      "durationMs": 9225
    },
    {
      "url": "https://nope.invalid.test",
      "status": "error",
      "error": "getaddrinfo ENOTFOUND nope.invalid.test",
      "startedAt": "2026-07-26T13:29:15.465Z",
      "finishedAt": "2026-07-26T13:29:17.235Z",
      "durationMs": 1770
    }
  ]
}
```

### `DELETE /api/jobs/:id`

Помечает задание как `cancelled` и возвращает его текущее состояние. Операция
идемпотентна: отмена уже завершённого задания ничего не меняет.

### Статусы

| Задание | Ссылка |
|---|---|
| `pending`, `in_progress`, `completed`, `cancelled`, `failed` | `pending`, `in_progress`, `success`, `error`, `cancelled` |

## Архитектура

### Бэкенд

```
backend/src/
├── main.ts                        точка входа, глобальная валидация, CORS
├── common/
│   ├── cancellation-token.ts      обёртка над AbortController
│   ├── task-pool.ts               пул задач с ограничением параллелизма
│   └── delay.ts                   прерываемая задержка
├── url-check/
│   ├── url-checker.service.ts     один HEAD-запрос → один результат
│   └── address-guard.ts           блокировка приватных адресов (см. ниже)
└── jobs/
    ├── jobs.controller.ts         только HTTP, без логики
    ├── jobs.service.ts            создание, список, детали, отмена
    ├── job-runner.service.ts      фоновое выполнение одного задания
    ├── jobs.repository.ts         хранилище в памяти
    ├── job.types.ts               доменная модель и формы ответов
    └── dto/create-job.dto.ts      валидация входных данных
```

`task-pool.ts` и `url-checker.service.ts` не зависят от Nest и тестируются изолированно.

Ограничение параллелизма сделано пулом воркеров: `limit` воркеров разбирают общий
курсор и перед взятием следующего элемента проверяют токен отмены. Поэтому отмена
останавливает именно то, что ещё не начиналось, как и требует ТЗ. У каждого задания
свой пул и свой токен, поэтому задания не мешают друг другу.

### Фронтенд

```
frontend/src/
├── api/          слой работы с API: client.ts, jobs.ts, types.ts
├── store/        глобальное состояние (Zustand)
├── hooks/        useJobPolling — опрос активного задания
└── components/   компоненты интерфейса
```

Опрос активного задания защищён от гонок тремя независимыми способами:

1. Цепочка `setTimeout` вместо `setInterval` — следующий запрос планируется только
   после завершения предыдущего, поэтому запросы не накапливаются.
2. `AbortController` на каждый запрос, прерывается в cleanup эффекта при смене
   активного задания или размонтировании.
3. Проверка в самом сторе: ответ с `jobId`, который больше не активен, не попадает
   в состояние. Это страхует случай, когда прерывание проиграло гонку у уже
   резолвящегося запроса.

## Принятые решения

ТЗ оставляет несколько вопросов открытыми. Ниже — принятые решения и их обоснование.

| Вопрос | Решение | Почему |
|---|---|---|
| Считать ли 404 успехом? | Ошибка, с сохранением `httpStatus: 404` и `error: "HTTP 404"` | Смысл проверки ссылок — найти нерабочие. Код `< 400` — успех, `>= 400` — ошибка. Так статистика «успешно / с ошибкой» становится осмысленной, и оба поля несут информацию. |
| Редиректы | Следуем, сохраняем итоговый статус | Пользователя интересует конечное состояние ссылки. |
| Серверы, отклоняющие HEAD (405/501) | Записываем как есть, без повтора через GET | ТЗ требует HEAD. Молчаливая подмена метода исказила бы то, что реально измерено. |
| Уже начатые запросы при отмене | Прерываются и помечаются `cancelled` | ТЗ требует остановить только не начатые. Отменять наполовину хуже, чем отменять полностью. |
| Отмена во время искусственной задержки | Результат HEAD отбрасывается, ссылка помечается `cancelled` | Консистентность важнее, чем сохранить результат, который пользователь просил не ждать. |
| Когда задание получает статус `failed` | Непредвиденная ошибка внутри раннера | Статус есть в ТЗ; оставить его недостижимым было бы небрежно. |
| Невалидная ссылка среди валидных | `400` со списком проблемных строк | Валидация на границе. Интерфейс показывает, какие именно строки неверны. |
| Занимает ли задержка слот параллелизма | Да | Задержка — часть обработки ссылки. Заодно ограничение в 5 одновременных проверок остаётся наглядным в интерфейсе. |
| Дубликаты ссылок | Сохраняются, не схлопываются | Это список пользователя и его намерение. |

Искусственная задержка 0–10 секунд выполняется **после** HEAD-запроса и **до** сохранения
результата, как указано в ТЗ, и поэтому входит в `durationMs`.

При остановке приложения все запущенные задания отменяются (`OnModuleDestroy`), чтобы
фоновые проверки не переживали процесс.

## Защита от SSRF

Сервис по своей природе делает исходящие запросы по ссылкам, которые прислал пользователь.
Если выставить его в публичный доступ как есть, он превращается в открытый прокси: через
него можно просканировать внутреннюю сеть или обратиться к адресу метаданных облака
`169.254.169.254`.

Переменная окружения `BLOCK_PRIVATE_ADDRESSES=true` включает защиту:

- имя хоста резолвится **до** запроса, и адрес проверяется по списку приватных и
  зарезервированных диапазонов (loopback, `10/8`, `172.16/12`, `192.168/16`, `169.254/16`,
  CGNAT, multicast, а также IPv6 `::1`, `fe80::/10`, `fc00::/7` и IPv4-mapped);
- в защищённом режиме редиректы обрабатываются вручную, и **каждый переход** проверяется
  заново. С `redirect: 'follow'` защита обходится тривиально: публичный адрес отвечает
  302 на приватный, и `fetch` переходит туда уже после проверки;
- редиректы на протоколы, отличные от `http`/`https`, блокируются.

По умолчанию защита **выключена**, чтобы локальный запуск и тесты вели себя ровно так, как
описано в ТЗ, и чтобы можно было проверять адреса вида `http://localhost:3000`.

Известное ограничение: имя резолвится при проверке и повторно при подключении, поэтому
теоретически возможен DNS rebinding. Закрыть эту щель полностью можно, только зафиксировав
адрес на момент соединения, чего `fetch` не позволяет.

## Ограничения

- Хранилище в памяти: после перезапуска бэкенда список заданий пуст. Граница вынесена
  в `JobsRepository`, поэтому замена на БД затронула бы только этот класс.
- Типы контракта продублированы в `frontend/src/api/types.ts`. Это осознанный выбор:
  общий workspace-пакет ради ~40 строк интерфейсов потребовал бы копирования корневого
  манифеста в оба Dockerfile и порядка сборки между образами.
- Таймаут HEAD-запроса фиксирован (10 секунд) и не настраивается через окружение.
